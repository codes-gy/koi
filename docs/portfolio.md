# Koi 프로젝트 회고

## 한 줄 소개

Koi는 Kotlin 문법을 바탕으로 Rust로 처음부터 구현한 인터프리터 언어입니다.
외부 라이브러리 없이 렉서, 파서, 인터프리터, REPL을 직접 작성했습니다.

## 이 프로젝트로 얻고자 한 것

### 1. 매일 쓰는 언어가 동작하는 원리를 직접 이해하기

코드를 쓸 때 당연하게 여기던 것들이 있습니다. `1 + 2 * 3` 이 왜 7인지, `if` 가 어떻게 값이 되는지, 블록 안에서 만든 변수가 왜 밖에서 보이지 않는지 같은 것들입니다.
책으로 읽는 것과 직접 만들어 보는 것은 다르다고 생각했습니다.
소스 코드가 토큰, 문법 트리, 실행 결과로 바뀌는 과정을 직접 구현하면서 이 규칙들을 동작하는 코드로 이해하는 것이 첫 번째 목표였습니다.

### 2. Rust를 실제 규모의 프로젝트에서 다루기

작은 예제로는 Rust의 장점과 어려움을 제대로 느끼기 어렵습니다.
언어 구현은 Rust가 잘하는 일에 가깝습니다. 문법 트리는 `enum` 으로, 문법 규칙은 `match` 로, 오류는 `Result` 로 표현할 수 있습니다.
소유권과 빌림 규칙 안에서 재귀적인 트리와 스코프 스택을 다루는 경험을 얻고자 했습니다.

### 3. 근거를 가지고 설계를 결정하는 연습

새 언어를 만들면 모든 결정을 스스로 내려야 합니다.
Kotlin을 기준으로 삼되, 각 기능마다 그대로 따를지, 바꿀지, 왜 그런지를 정하고 기록했습니다.
"원래 그렇게 되어 있어서"가 아니라 "이런 이유로 이렇게 했다"고 설명할 수 있는 개발자가 되는 것이 목표였습니다.

### 4. 테스트로 동작을 지키는 습관

기능을 하나 추가할 때마다 사용자가 보는 동작(출력 결과, 오류 메시지)을 기준으로 테스트를 썼습니다.
덕분에 문법을 Kotlin 스타일로 크게 바꿀 때도 기존 동작이 깨지지 않았는지 바로 확인할 수 있었습니다.

### 5. 사용자 경험까지 생각하는 개발

언어의 사용자는 그 언어로 코드를 쓰는 사람입니다.
오류 메시지에 줄 번호와 고치는 방법을 함께 보여주고, REPL에서 여러 줄 입력을 자연스럽게 받는 것처럼, 기능이 "동작하는 것"을 넘어 "쓰기 편한 것"까지 신경 쓰고자 했습니다.

## 왜 Kotlin을 기준으로 삼았나

Kotlin은 Android와 서버 개발에서 널리 쓰이는 언어이고, 간결하면서도 실수를 줄이는 문법이 많습니다.
특히 아래 기능들은 작은 언어에 넣어도 효과가 크다고 판단했습니다.

- `val` / `var` 로 바꾸지 않을 값과 바꿀 값을 문법에서 구분합니다.
- `if` 와 `when` 이 값을 돌려주는 식이라, 임시 변수 없이 `val 등급 = if (...) "A" else "B"` 처럼 쓸 수 있습니다.
- 문자열 템플릿 `"$이름님"` 이 `+` 로 이어 붙이는 것보다 읽기 쉽습니다.
- `1..10`, `x in 범위` 같은 범위 문법이 반복문과 조건을 짧게 만듭니다.

## 주요 설계 결정

| 결정 | 이유 |
|---|---|
| **Pratt 파서** | 연산자 우선순위를 표 하나(binding power)로 관리합니다. Kotlin의 우선순위 9단계를 이 표에 옮겼고, 새 연산자는 표에 한 줄을 추가하면 됩니다. |
| **트리 순회 인터프리터** | 구조가 단순해서 언어 기능을 빠르게 추가하고 검증할 수 있습니다. 성능이 필요해지면 바이트코드 VM으로 바꿀 계획입니다. |
| **`Int` 와 `Double` 분리** | Kotlin과 같이 `10 / 4` 는 `2`, `10 / 4.0` 은 `2.5` 입니다. 처음에는 숫자를 하나로 두었지만, Kotlin 사용자가 예상하는 동작과 맞추기 위해 나눴습니다. |
| **정수 오버플로는 오류로 처리** | Kotlin은 `Int` 가 넘치면 조용히 음수가 됩니다. Koi는 Rust의 checked 연산으로 이를 오류로 알립니다. 조용히 틀린 값을 내는 것보다 명확한 오류가 낫다고 판단해서 Kotlin과 다르게 결정했습니다. |
| **`break` 위치를 실행 전에 검사** | 반복문 밖의 `break` 는 파서가 실행 전에 거부합니다. 프로그램이 절반쯤 실행된 뒤에 실패하지 않습니다. |
| **REPL의 미완성 입력 감지** | 파서가 "입력이 끝나서 멈춘 오류"와 "진짜 문법 오류"를 구분합니다. 앞의 경우에만 REPL이 다음 줄을 기다립니다. |
| **한글 변수 이름과 한국어 오류 메시지** | 한국어 사용자가 처음 프로그래밍을 배울 때도 쓸 수 있게 했습니다. 오류 메시지의 타입 이름은 Kotlin과 같이 `Int`, `String` 으로 보여줍니다. |
| **스코프를 스택에서 체인으로** | 처음에는 블록이 끝나면 버리는 스코프 스택을 썼습니다. 클로저는 블록이 끝난 뒤에도 그 변수를 써야 하므로, 스코프를 `Rc<RefCell<Scope>>` 로 공유하는 체인으로 바꿨습니다. |
| **함수 타입은 실행할 때 검사** | Koi는 정적 타입 검사기가 없습니다. 대신 Kotlin처럼 매개변수에 타입을 반드시 적게 하고, 호출할 때 값이 그 타입인지 검사합니다. `Double` 자리에 `Int` 를 넣으면 Kotlin처럼 오류입니다. |
| **최상위 함수는 어디서든 호출** | Kotlin처럼 파일 아래쪽에 선언한 함수도 위에서 호출할 수 있습니다. 실행 전에 최상위 `fun` 을 먼저 등록합니다. |
| **재귀 깊이 제한 5,000** | 트리 순회 인터프리터에서 Koi 함수 호출은 Rust 함수 호출 여러 겹이 됩니다. 끝나지 않는 재귀가 프로세스를 죽이지 않도록 깊이를 제한하고, 측정한 스택 사용량에 맞춰 인터프리터 스레드의 스택 크기를 정했습니다. |
| **null 안전성은 실행 중 검사** | `String` 변수에 null을 넣는 순간 오류를 냅니다. Kotlin은 이를 컴파일할 때 막지만, Koi는 정적 타입 검사기가 없어서 값이 들어가는 시점(선언, 대입, 함수 호출, 반환)에 검사합니다. 오류 메시지는 `String?` 로 선언하라고 안내합니다. |
| **타입을 적지 않은 변수도 타입이 있음** | null 안전성이 의미가 있으려면 `var 이름 = "Koi"` 에 나중에 null이나 숫자를 넣는 것도 막아야 합니다. Kotlin처럼 첫 값으로 변수 타입을 정하고, 대입할 때마다 검사합니다. |
| **`return`, `break`, `continue` 를 식으로** | Kotlin에서 이들은 식이라서 `val n = 입력 ?: return` 같은 관용구가 가능합니다. 처음에는 문장으로 만들었지만, `?:` 를 넣으면서 식으로 옮겼습니다. |
| **외부 라이브러리 없음** | 파서 생성기 같은 도구를 쓰지 않고 모든 단계를 직접 구현해서 원리를 이해하는 데 집중했습니다. |

## 기억에 남는 문제와 해결

**한글과 문자열 템플릿의 충돌.**
Kotlin 규칙을 그대로 따르면 `"$나이살은"` 은 `나이살은` 전체를 변수 이름으로 읽습니다.
영어는 단어 사이에 공백이 있어서 드문 문제지만, 조사가 이름에 바로 붙는 한국어에서는 자주 생깁니다.
규칙을 바꾸면 Kotlin과 달라지고 규칙이 복잡해지므로, 규칙은 유지하고 이 상황에서 오류 메시지가 `"${나이}살은"` 으로 고치라고 안내하도록 했습니다.

**`for` 문의 마지막 정수.**
`for (i in 1..최댓값)` 을 단순하게 `i += 1` 로 구현하면, 마지막 값에서 정수가 넘칩니다.
마지막 값에 닿으면 증가시키기 전에 멈추도록 구현하고, `Int` 최댓값까지 도는 테스트를 추가했습니다.

**재귀 깊이 제한 정하기.**
끝나지 않는 재귀를 실행하면 Rust 스택이 넘쳐서 프로세스가 오류 메시지도 없이 죽었습니다.
호출 깊이에 제한을 두기로 했지만, 숫자를 감으로 정하고 싶지 않았습니다.
그래서 재귀 깊이별로 필요한 스택 크기를 측정하는 프로그램을 따로 만들었습니다.
측정해 보니 Koi 호출 한 번에 debug 빌드는 약 19.4KB, release 빌드는 약 2.2KB를 썼고, 깊이와 정확히 비례했습니다.
이 숫자로 제한(5,000)과 스레드 스택 크기(512MiB, debug 기준 약 5배 여유)를 정했습니다.
마지막으로 깊이 검사를 일부러 지워서, 테스트가 실제로 이 문제를 잡아내는지 확인했습니다.

**null 안전성을 넣다가 변수 타입까지 넣게 된 일.**
처음 계획은 `null`, `?.`, `?:` 만 추가하는 것이었습니다.
그런데 변수에 타입이 없으면 `var 이름 = "Koi"` 다음에 `이름 = null` 을 막을 방법이 없어서, null 안전성이 이름뿐인 기능이 됩니다.
그래서 변수에 타입 표기를 추가하고, 표기가 없으면 첫 값으로 타입을 추론하도록 범위를 넓혔습니다.
`?.` 를 쓰려면 `.` 이 먼저 있어야 해서 문자열과 숫자의 멤버(`length`, `toIntOrNull()` 등)도 함께 만들었습니다.

**예제를 실행하다 찾은 문법 버그.**
`?.let { }` 체인을 여러 줄로 쓴 예제를 실행했더니, 줄 맨 앞의 `?:` 를 읽지 못했습니다.
Kotlin 문법을 확인해 보니 `?:`, `&&`, `||` 앞의 줄바꿈은 허용하지만, `+` 나 `-` 앞은 허용하지 않았습니다. 줄 맨 앞의 `-5` 는 새 문장이기 때문입니다.
같은 규칙으로 고치고, 두 경우를 모두 테스트로 남겼습니다.

## 알려진 한계

- 함수가 자기가 만들어진 스코프를 붙잡고, 그 스코프가 다시 함수를 붙잡으면 참조 순환이 생깁니다. 지금은 이런 메모리를 회수하지 않습니다. 짧게 실행하는 스크립트에서는 문제가 되지 않지만, 오래 실행되는 프로그램을 지원하려면 가비지 컬렉터가 필요합니다.
- 타입 검사와 null 검사가 실행 중에 일어나므로, 실행되지 않은 코드의 오류는 찾지 못합니다. Kotlin처럼 실행 전에 잡으려면 정적 타입 검사기가 필요하고, 이것이 다음 큰 목표입니다.

## 현재 상태

- 인터프리터 Rust 코드(`src/`) 약 2,500줄, 외부 라이브러리 0개
- 동작 테스트 127개
- 지원 기능은 [README의 문법 표](../README.md#문법)에 정리했습니다.
